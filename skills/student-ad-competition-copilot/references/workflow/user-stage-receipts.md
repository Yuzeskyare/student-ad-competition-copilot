# 用户可见阶段回执协议

默认完成边界：交付作品。当前赛事规则、实际提交规格与外部研究引用在完成前核对；素材/字体使用依据、AIGC后台记录及平台申报仅完成后提醒，报名身份、上传和回执不阻断作品完成。
阶段回执把运行包中的实际状态翻译成用户能核对的简短说明。它不替代`run-status.json`、`quality-gate-results.json`或人工评审记录，也不能产生这些记录中不存在的通过状态。

## 何时给出

在以下时点给出回执：

1. 一个赛道阶段或当前运行范围完成；
2. 质量门进入`fail`或`blocked`并改变后续路径；
3. 必须等待用户材料或人工决定；
4. 恢复运行并从保存状态确定继续位置；
5. 用户要求的范围已经完成。

不要为同一阶段中的每个后台字段、文件写入或自动检查单独发回执。连续微步骤只在状态发生上述变化时合并报告。

## 最小格式

每张回执包含四项，优先使用普通创作语言：

- `本阶段`：刚完成、失败、阻塞或恢复的阶段，以及本次覆盖范围；
- `已核对`：用户可理解的关键产物和证据，必要时附路径，不罗列内部字段；
- `当前状态`：`passed`、`passed-with-boundaries`、`failed`、`blocked`或`scope-complete`，并分别说明技术、内容、方法与作品交付状态；仅用户另行要求实际投稿时说明投稿状态；
- `唯一下一动作`：一个具体动作，包含对象与目的，不写“继续推进”“再完善”等泛词。

`passed-with-boundaries`必须列出尚未解决的边界，以及它限制的是概念、生产、交付还是投稿。阶段通过只表示该阶段和声明范围通过，不表示后续阶段、未审版本或整项赛事作品通过。

## 唯一下一动作

根据依赖和当前状态只输出一个主动作：

- 有已观察失败：回到质量门声明的最近责任阶段，修复该具体关系；
- 有硬阻塞：取得解除最先阻塞项所需的官方材料、保真资产、许可或用户决定；
- 需要人工审核：展示当前检查点，最短回复作为唯一动作；
- 当前阶段通过且目标范围未完成：进入首个未完成且依赖已满足的阶段；
- 当前请求范围完成：`无，当前请求范围已完成`。

存在多个问题时，其他问题保留在“开放边界”中，不把它们并列成多个下一动作。首个动作完成后再依据新状态计算下一动作。可选扩展不能伪装成当前任务的必需下一步。

## 状态用语边界

- `technical_pass`只说明可客观检查的文件、字段、尺寸、计数或结构通过；
- `content_pass`只说明真实人工已确认的版本和范围通过；
- `method_validated`只说明方法在声明范围内走通；
- `delivery_complete`：当前作品通过内容和适用技术/视觉验收，当前赛事规则、实际提交规格及外部引用已核对并交付；权利手续、AIGC记录与平台申报仅交付后提醒。

当技术通过而内容待审时，应写“技术检查通过，内容确认待完成”，唯一下一动作是对应人工检查点。恢复运行时先从保存状态重新计算，不沿用已经过期的文字回执。用户指出新问题或输入发生实质变化后，更新受影响状态，再生成新回执。

## 示例

```text
本阶段：广告文案入围稿已完成，范围为 production-candidate。
已核对：4份入围稿的命题事实、品牌关联和朗读差异。
当前状态：技术项通过；内容通过待人工确认。开放边界是最终稿尚未选定。
唯一下一动作：查看4份入围稿并回复“选B”或指出一个具体问题。
```
